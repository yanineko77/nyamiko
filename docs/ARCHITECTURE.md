# Nyamiko: как это работает

## Почему не mihomo

Ядро webOS 4.x (Linux 4.4) собрано **без policy routing**: `ip rule` отвечает
`Operation not supported`. mihomo/Clash при поднятии TUN всегда добавляет правила
маршрутизации и падает с `configure tun interface: add rule 0/1`. sing-box умеет
TUN без этого (`auto_route: false`), поэтому он и выбран.

## Маршрутизация (без policy routing)

```sh
ip route del default via "$GW" dev "$IFACE"          # убрать маршрут менеджера сети
ip route replace default dev sbtun metric 0           # весь трафик в туннель
ip route replace default via "$GW" dev "$IFACE" metric 100   # резерв для своих сокетов
ip route add "$SERVER_IP/32" via "$GW" dev "$IFACE"   # пин сервера VPN
```

- Метрика **0** обязательна: менеджер сети (connman) возвращает свой маршрут с
  метрикой 0 и иначе выигрывает.
- У каждого outbound в конфиге ядра стоит `bind_interface: wlan0`, поэтому
  собственные сокеты клиента уходят через физический интерфейс, а не в туннель.
- Сторож каждые 20 секунд проверяет, что маршрут на месте, и возвращает его.

## Узлы и переключение

Все узлы подписки генерируются как отдельные outbound'ы `n0..nN` и попадают в
группу `selector` (`vpn`). Ядро поднимает Clash-API на `127.0.0.1:9090`:

- переключение узла: `PUT /proxies/vpn {"name":"n12"}` — мгновенно, без
  перезапуска и без разрыва;
- замер: `GET /proxies/n12/delay?timeout=3000&url=<generate_204>`.

`urltest` внутри ядра мы **не используем**: на 90 узлах телевизор захлёбывается
(в логах DNS-запросы висели по 17 секунд). Замер делает панель, порциями по 5.

## Автопереключение (перенос схемы с телефона)

- каждую минуту — проба канала через активный узел;
- 3 провала → перебор ~10 кандидатов (по 3 одновременно), включая текущий узел, и
  пересадка только если победитель **действительно** лучше;
- 2 удачные пробы → успокоиться; между переключениями минимум 10 минут;
- раз в 5–10 минут — проверка «нет ли быстрее» (пересадка при выигрыше ≥25 %);
- счётчики видны в панели и API (`sup`), каждая смена пишется в лог.

## Подписка

Профиль тянется **только при опущенном туннеле**: панели с привязкой к устройству
(Remnawave и родственники) отдают заглушку `App not supported`, если запрос
приходит с VPN-выхода. Отсюда:

- `x-hwid` считается из MAC-адреса телевизора и уходит только в запросе подписки;
- при неудачной загрузке используется последний удачный профиль (`*.good`);
- раз в сутки профиль обновляется: `down` → `fetch` → `up`.

## Файлы на телевизоре

| Путь | Что это |
|---|---|
| `/media/internal/tv-tunnel/sing-box` | ядро |
| `.../genconfig.py`, `yamlite.py` | парсер подписки (Clash YAML) и генератор конфига |
| `.../tunnelctl.sh` | управление туннелем, маршруты, сторож |
| `.../tvtunnd.js` | панель (:8099) + API + автопереключение |
| `.../ui.html` | интерфейс |
| `.../config.json` | настройки и ключи (600) |
| `.../state/` | состояние, метки времени |
| `.../*.log` | логи (обрезаются сторожем) |
| `/var/lib/webosbrew/init.d/60-tvtunnel` | автозапуск |
| `/var/lib/webosbrew/init.d/55-ca-extra` | добавка корневых сертификатов |
